# Craft Anything 项目分析

Craft Anything 将软件分析工具、证据记录、AI 编码和结果检查组合起来，适合辅助研究软件和生成重建初版。它已有较完整的分析基础，但现有 Web 程序只是轻量文件查看器；要交付类似 WordCraft 的 Agent 实时 Web 软件，还需按本目录的方法补齐领域编辑、当前页面控制、保存与平台链。

## 2. 产品构成与工作流

普通用户选择网站、应用、游戏或描述，经过 Study→Build→Check→Ready；高级工作台可以查看函数、反汇编、伪代码、字符串、调用图、证据和未知项。静态分析通常不需要 AI，生成项目需要编码 Agent 或 API 模型。

入口分别是原生 egui 桌面、CLI、stdio MCP 和浏览器查看器。CLI/MCP 提供完整引擎入口，浏览器只运行受限的 WASM 安全模块，不能按“同一项目有 Web 包”推断产品等价。

研究与重建工作区主要保存：

| 路径 | 内容 |
|---|---|
| `craft.json` | 请求、目标、状态、检查历史与构建信息 |
| `investigation.cany/` | 分析项目、证据、未知项、记忆与日志 |
| `capture/`、`reference/` | 观察材料与用户参考图 |
| `app/` | 生成项目，支持已有项目原地编辑等其他模式 |
| `checks/` | 每轮检查和截图 |
| `inbox/` | 问题、授权及构建进度记录 |
| `transcript.json`、`usage.json` | 内置 API 对话与用量记录 |

本地记录可恢复工作和解释过程；它们不具备 IntegrateCraft 实例外追加审计的权限边界。

## 3. 架构与代码分布

| 层 | 模块 | 非 vendor Rust 行数，含测试 | 职责 |
|---|---|---:|---|
| L0 | evidence | 895 | 统一证据、错误与未知项 |
| L0 | formats | 45,599 | 多格式纯解析，包含大量边界回归 |
| L1 | disasm / js | 5,845 / 5,557 | 原生代码和 JS 分析 |
| L2 | analysis / platform | 10,212 / 6,208 | 分析工作流、进程、文件与同步 |
| L3 | engines | 9,030 | 外部引擎与浏览器/设备适配 |
| L4 | engine | 56,098 | Session、项目、工具和权限 |
| L5 | ai / mcp / setup | 26,752 / 1,348 / 2,655 | 模型编排、协议服务和连接 |
| L6 | ui-egui | 21,212 | 原生界面 |

其余为应用入口、testkit、xtask 和示例。生产依赖按层向下，使用 `xtask layers` 约束；本次 metadata 生产边核对未发现注册模块反向依赖。完整 xtask 检查未运行。

`Engine::call` 是统一入口：查工具→获取 Session→检查模式/依赖→检查执行授权→运行并捕获可展开的 panic→记录证据与日志。工具用 `ToolSpec` 声明 ID、schema、说明、工具集、副作用与执行函数。

一个 Engine 执行工具时持有同一 Session 锁，因此同 Session 长工具会串行占用。UI 使用后台线程及 try-lock，重建工作另有运行队列。服务器化时应按任务/用户设计会话隔离，不能把协议可并发读请求当作内核并发吞吐保证。

## 4. 各方向能提供的能力

| 方向 | 源码能力 | 实际限制 |
|---|---|---|
| 原生程序 | PE/ELF/Mach-O 等识别、函数、CFG、xref、调用图、寄存器数据流和伪 C | 伪 C 没有完整类型恢复；未知指令与非结构化控制流有回退 |
| JavaScript/Electron | OXC 解析、bundle/模块线索、IPC、source map、应用图与对比 | 高嵌套/大源降级词法扫描；运行时目标需可调试 |
| .NET / Java | 元数据、IL/类结构；Java 可调用 Vineflower | .NET 不等于完整 C# 恢复；外部工具能力按实际安装 |
| Android / Apple | APK/DEX、资源、Mach-O 与平台元数据、设备/运行工具 | 很多设备工具缺实机验证；系统工具受 OS 和权限约束 |
| 固件/数据库/网络 | 多文件系统、压缩、SQLite、pcap/HAR 等分析 | 格式边界多，部分版本/压缩类型尚不完整 |
| 游戏资源 | Unity、Unreal、Godot、IL2CPP 等识别和部分提取 | 音频/网格、复杂压缩和新格式版本仍有缺口 |
| 调试/动态观察 | CDP、adb、GDB、Rizin、Frida 等适配 | 部分依赖外部程序；Frida 持续会话未完整实现 |
| 重建 | 研究、构建说明、Agent 生成、检查与继续修正 | 对领域规则、文件兼容和全交互的证明仍有限 |

原生分析主体自行实现高层逻辑，指令解码依赖现有库。Ghidra 为 Deep 模式下的可选增强。所谓纯 Rust 核心不代表全部依赖不含原生代码，也不代表外部工具、macOS Swift helper 或 Windows PowerShell helper 都不需要系统环境。

## 5. 证据设计及价值

证据记录 subject、operation、params、result、environment、confidence、authority、coverage、limitations 与 locations。置信类型区分 Observed、Derived、Inferred；未知项可以记录所需的补证方法。

ID 来自规范化内容的 SHA-256，加载时校验摘要与身份。这能发现持久记录被改动；它不能证明观察工具本身没有错误，也不能让模型推断自动变成观察事实。

这种设计值得借鉴到各款软件的检查输出：把实际状态、推导结论和未验证项分开。但编辑器命令不必全部返回庞大分析证据，保留本款原生契约即可。

## 6. AI 与扩展结构

AI 层支持 Anthropic、OpenAI/OpenRouter、Gemini 的兼容端点、本地兼容服务、Agent CLI 和 SSH 等路径；适配器和 ACP 的工具、会话恢复、审批能力不同。Claude Code 接线较完整，其他后端需要按锁定版本逐项核实。

内置 API loop 负责工具执行、上下文压缩与续接。源码有默认 40 轮一般交互、400 轮 builder 单步上限、25 次连续失败构建命令守卫；重建还会检查连续两轮没有文件变化和跨运行连续不可用检查。通用 token/费用硬上限仍有待决策工作。

插件方面，它可作为 MCP 客户端接本地 stdio 或远程 Streamable HTTP 服务，也有默认关闭的 WASM component 插件功能。工具结果按外部来源记录，插件配置默认要求执行授权。

## 7. 重建检查的证明力

网站检查默认宽度为 1440、768、390，默认额外页面数为 4，可配置且存在上限。保存截图、可见内容和测量信息，并比较部分菜单/弹层等状态。视觉分数主要由布局与图像相似性计算，其他内容断言和未比较项参与严格检查。

桌面应用主要检查构建、运行和截图；有运行时观察材料时可比较窗口和控件。游戏额外要求 `--self-test`，读取 move/act/hud 三步报告。报告由生成程序自己写，关键玩法仍需外部观察或独立测量。

`CheckResult::good()` 要求可运行、无 unknown、全部 claims 成立、相似度达到阈值。达到修正上限后，可用产物仍可能被置为 `Ready` 并附不足说明。因此，自动验收必须看具体检查，不把状态字符串当全链通过。

仓库记录过 Windows 网站和小应用重建，也记录了本地小模型只写出可编译 Hello World、未完成计算器而被检查拒绝的案例。API Key 与默认 Clean room 完整链等仍有实测欠账，不能推广为各模型都可稳定重建软件。

## 8. 源码核到的优先问题

| 问题 | 源码依据 | 对使用的影响 |
|---|---|---|
| 策略设置可由工具改变 | `settings_set` 白名单允许，能改 `deep_mode/ask_before_running`，无相应强制执行审批 | 宿主需限制策略工具；显式进程模式可锁当次 Clean room |
| macOS 失败包装为证据 | helper 权限不足输出 error/空 nodes 并退出 0，Rust 未提升为错误 | 空结果可能被标成 Observed，需修错误传播 |
| Frida 会话部分为记录 | `frida_tools.rs` 明确记录 attach/spawn 意图，脚本按 bounded CLI 执行 | 不能宣称完整持续动态会话 |
| Ready 语义宽于质量通过 | 重建到修正上限后看可用性设置 Ready | 需分别报告可用与验收 |
| 后端禁用状态不一致 | 命名选择 `builder_backend` 直接 `cfg.get`，未核 enabled | 指定禁用后端仍可被选到 |
| 运行证据不均衡 | tool-status、STATUS 和 ROADMAP 仍列设备/模型/OS 未测 | 能力按环境分级提供 |

这些是静态核查和仓库已登记问题；本次未复现实机故障、未修代码。Clean room 是工具访问策略，外部程序仍需要操作系统隔离。

## 9. MCP 与配置上的实际契约

服务端为 stdio JSON-RPC，默认渐进显示 Core，支持工具集发现、启用、进度、取消、证据资源与引导 prompts。服务端输出文本和 structuredContent，大结果有预算、摘要及证据引用。

CLI 的全局 `--project` 用于 `.cany` 调查项目，不能当成重建 workspace 参数。重建工具另有 `project/projects_dir/project_folder` 等字段，按对应 schema 传。CLI 支持 `--deep/--clean-room/--allow-run`；MCP 支持 `--all-tools/--inbox/--target`。未核到其他 Craft 常见的 automation read/write roots 参数，不能照搬。

`CRAFT_ANYTHING_CONFIG_DIR` 可固定配置、日志和引擎仓库目录。默认设置会发现本机后端、插件和工具，平台应生成受控配置并限制发现范围。`--allow-run` 把调用视为已授权，不适合作为省去审批的通用配置。

工具集的“未显示”不构成拒绝边界：`call_engine` 能自动启用被调用的工具集。平台要在真实执行入口做策略校验，不能只删列表项。

## 10. 工程质量与维护成本

项目有分层、锁检查、格式/Clippy/测试、WASM 检查、工具/Schema 生成一致性与秘密扫描。外部程序统一通过有超时、输出上限、取消及进程组清理的封装运行；自身代码禁 unsafe，并集中处理异常。

解析、引擎工具和 AI 适配器范围广，维护成本主要来自输入格式变化、外部工具契约和跨平台行为。若用于本项目，优先提供经过核实的能力子集，扩展时按完整结果补证。
