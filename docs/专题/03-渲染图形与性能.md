# 渲染图形与性能

输入是领域状态、资源、视口和输出规格；输出是可见、可导出的同一作品。屏幕与导出可以使用不同分辨率，但应共享相同领域表示和明确的绘制语义。

## 选择渲染路径

| 路径 | 适合的起点 | 先核实的限制 |
|---|---|---|
| DOM/SVG | 文本与结构交互、小中规模矢量 | 大量节点、复杂滤镜、布局和字体 |
| Canvas 2D | 自绘画布、位图与二维编辑 | 文本输入另接、命中索引、重绘和内存 |
| WebGL/WebGPU | 三维、复杂合成、GPU 计算 | 目标浏览器、驱动、资源生命周期和回退 |
| 原生内核渲染到图像 | 现有布局/渲染器可复用 | 传输、交互命中、延迟和部署成本 |

按领域和目标设备选，先做一份真实复杂样本。不得把“支持某 API”推断为本款渲染和内嵌部署都成立。

## 渲染状态与调度

文档修订和资源修订共同决定渲染输入。每个任务带目标文档/修订，旧任务完成后不覆盖新画面。合并同帧内多次失效请求；对长计算取消旧任务，避免拖动时排满永远画不完的队列。

先全量正确重绘，再根据测量引入 dirty region、分块、缓存或层合成。缓存键应覆盖字体、样式、资源、缩放等真正影响结果的输入；缓存只是加速，不应成为无法重建的作品真相。

## 像素与资源

区分世界单位、CSS 像素和设备像素。导出尺寸使用用户选择的明确规格；选择框、辅助线等编辑器覆盖层是否导出写入契约。

字体、图片和模型异步加载完成后再确认相关渲染可用；缺失资源用可解释的错误/占位反馈，不能输出空图却说渲染成功。字符内容和字形都要验证，尤其是中文和混合字体。

大 RGBA 图像的基础缓冲成本约为宽×高×4 字节，多个中间层还会相乘。限制画布尺寸、离屏层和缓存预算，流式/分块处理超大输入；测量时同时看 JS 堆、WASM 内存与 GPU 资源。

## Worker 与异步边界

昂贵计算移到 Worker 时，明确谁拥有状态和缓冲；传输后发送方不应继续使用已转移资源。`OffscreenCanvas` 可在 Worker 中绘制，但具体上下文与浏览器支持仍需测量，见 [MDN](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas)。

Worker 不是第二个随意修改的文档副本。用版本化快照或命令序列同步，结果带请求身份与修订，只有当前结果能提交。需要共享内存时另核并发与部署前提。

## 性能验证

建立固定样本：少量对象验证正确性、大量对象验证交互、复杂资源验证加载。分别测冷启动、打开、单命令、首次可见、拖动和导出；记录设备、视口、输入和分位结果。

先定位时间花在哪：解析/计算、消息传输、状态派生、布局、绘制、解码或上传。只优化实际热点，优化后以相同样本对比内容与画面。不能通过减少必要内容或降低输出规格取得假性能提升。

## 练习与故障处理

矩形示例在 DPR 1/2 下应保持世界坐标和导出规格相同；Agent 移动后截图对应最新修订。模拟图片迟到、Worker 旧结果、窗口缩放和 GPU/context 丢失，检查错误、恢复和资源释放。

交付渲染契约、资源预算、就绪信号、截图接口、性能样本与故障恢复。性能门槛由实际用户任务确定。
