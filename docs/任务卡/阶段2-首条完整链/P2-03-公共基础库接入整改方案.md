## 给你看的

建议采用“按能力分批接入公共库”：让公共库承担标准编码、受限消息读取、文件刷盘和通用测试辅助，Draft继续负责晶体业务、事务历史、身份、资源拥有权和可信保存。这样可以减少通用代码的重复实现，同时保留现有工程文件和已证明的结果。

本次盘点了本地craft-libs的**199个crate声明**，重点筛选43个基础能力候选，固定122份说明、声明或源码输入。其余156个主要是具体格式或领域库，本卡不整包引入。这个数字是盘点范围，不是199个库都经过逐行审计或编译验收。

| 决策 | 建议采用的能力 | 对现有Draft的影响 |
|---|---|---|
| 直接集成 | craft-jsonrpc的有界行读取；craft-mime的严格Base64；craft-testkit的适用测试辅助 | 替换相应通用算法，保留Draft的协议形状、配额和错误类别。testkit只作为开发依赖 |
| 适配接入 | craft-atomic的文件同步原语 | 保留Draft的授权目录、目标基线、资源目录先行和主文件最后发布顺序；不直接调用公共库的整套保存流程 |
| 后续按需求接入 | MCP前端、页面桥、配置/快捷键、本地化及格式识别等公共能力 | 尚无对应现行消费者的，不提前增加框架或空接口；届时通过薄适配层连接同一个Engine |
| 保留自研 | 晶体/科学模型与算法、NS2状态机、Source7生成访问器/codec、fresh身份、资源lease、事务/历史、HS4保存结算 | 这些规则受Draft已确认合同约束，公共库当前没有提供等价实现 |

几处不能整套替换的差异已经核实：

- craft-format和craft-document-bundle使用ZIP容器；Draft已确认采用`.vesta＋资源目录`，本轮不更换保存格式。
- craft-atomic的整套writer会跟随符号链接，目录同步失败按best effort处理；Draft现有目录拒绝和错误传播要求不同。可以复用其小原语，不能直接换掉现有发布策略。
- craft-web-host的普通`saved`通知可用于清dirty，旧兼容方式甚至把“已发出”当作保存完成；Draft的HS4要求可信宿主操作和语义恢复证明，不能照搬。
- craft-jsonrpc的JSON-RPC信封和普通JSON解析不是NS2；只复用行读取，不能把seq、epoch、重放、取消或严格JSON检查交给另一套协议。

P2-03仍然partial。前轮两条CLI驱动失败及未到达的旧四件迁移、协议生命周期矩阵必须保留；引入公共库不能替代这些验证。**累计138.027328167/14400秒、测试14/14、保守冷构建3/3、无新获取、产品停跑保持。** 本方案没有申请、分配或消费新测试组，也没有授权依赖获取或构建。

### 3. 首批：明确接入的四项能力

#### 3.1 craft-jsonrpc：直接复用有界行读取

- 实际API：[read_line](/Volumes/T9/Development/Sources/Artcraft/craft-libs/crates/jsonrpc/src/lib.rs) `read_line<R: BufRead>(&mut R, max_bytes) -> Result<Option<Vec<u8>>, LineError>`。无默认async功能；生产依赖只有serde_json，`async-lines`必须关闭。
- 现有位置：[stdio.rs](/Users/agilecho/code/VestaDraft/app/kernel/crates/cli/src/stdio.rs)的fill_buf/consume拼帧循环。
- 拟新增`app/kernel/crates/cli/src/frame_io.rs`，提供`read_ns2_frame<R: BufRead>(&mut R) -> Result<Option<Vec<u8>>, FrameReadError>`，错误闭合为`Io(std::io::Error)`或`TooLong`；底层调用公共read_line，保留原stdio线程、mpsc容量8、推进/取消时序和Session.handle入口。
- 边界必须兼容现实现：当前LF计入1,048,576物理帧字节，LF随后剥离；无LF的EOF帧按实际字节计。公共read_line的max不计LF，因此包装层须用一个记录consume字节数/末尾LF的BufRead计数器核限，不能直接传同一个max就宣称等价。CR保持现行为，UTF-8继续由现有层检查。
- 空行仍交给NS2严格解析处理；EOF仍区分干净退出和未结算snapshot的exit3。TooLong映射原N_FRAME并终止该读流，不能继续把剩余半行当下一请求。
- **不调用**`request/process/process_legacy/control::process_line`，也不用`parse_json`替代model::json::parse：公共普通serde_json解析会丢失重复键拒绝/节点预算等Draft约束。NS2信封、九摘要、seq/context/重放和错误union原字节保持。

#### 3.2 craft-mime：直接复用严格RFC4648 Base64

- 实际API：[base64::STANDARD](/Volumes/T9/Development/Sources/Artcraft/craft-libs/crates/mime/src/base64.rs)的encode/decode；标准+/字母表、必须padding、零unused bits、拒绝空白，满足现有canonical要求。
- 现有位置：[base64.rs](/Users/agilecho/code/VestaDraft/app/kernel/crates/cli/src/base64.rs)。保留该文件的`encode(&[u8])->String`、`decode(&str)->vesta_model::Result<Vec<u8>>`作为限额/错误包装，删去A表、移位和重复编码算法。
- 编码调用STANDARD.encode；解码先保留输入≤87,384字节与长度%4检查，再STANDARD.decode，最后保留输出≤65,536字节，所有失败映射原N_SCHEMA。不使用兼容MIME transfer解码、optional padding或URL-safe配置。
- 采用完整上游crate，不把base64源文件复制进自研crate后再称公共crate集成。`default-features=false`，不启用detect。**成本明确**：该crate仍有mandatory craft-codepage、encoding_rs、chrono依赖，不能把这个选择描述为“无新依赖的小函数替换”。若未来受控依赖解析表明超出明确获准的获取/构建范围，停此项，保留原模块，不临时换库或手抄源算法。

#### 3.3 craft-atomic：适配文件同步，保留Draft发布策略

- 现有位置：[Paths::publish](/Users/agilecho/code/VestaDraft/app/kernel/crates/cli/src/paths.rs)，负责root拒绝、目标hash基线、先依赖后主文件、临时文件、二次基线检查、rename、父目录同步及实际读回。
- 首批只在CLI原生I/O边界调用公共`craft_atomic::sync_file(&File)->io::Result<()>`，替换资源文件、主文件临时文件及父目录文件句柄的sync_all；获得Apple F_FULLFSYNC与已有回退逻辑。拟集中在`cli/src/native_io.rs`，方便定向故障注入。
- 保留现有Paths授权根/逐级symlink拒绝、immutable dependency字节碰撞检查、create_new、资源布局、nonce和主文件最后提交。父目录同步错误继续向上传播，不能被公共整套writer的best effort吞掉。读回与hash比较仍由Draft负责。
- **首批不调用atomic_write/write_new及其custom变体**：其入口在可注入AtomicFs之前就resolve_links和检查目标；write_new在硬链接失败时还会copy到最终名，目录同步错误被忽略。简单包一层Paths检查或自定义rename并不能证明这些语义完全相同。
- retry_rename暂不引入默认Windows重试；如后续需要，必须每次重试均重新核baseline/root，并计入同一执行时限。现rename/错误结果不因“公共库默认”静默改变。
- 不把公共sync成功登记为HS4 Saved；此处仍只是工程fixture原生I/O，真实个人空间落盘由宿主负责。现D2-13检查/使用竞态边界继承，不声称新增了跨平台无竞态保证。

#### 3.4 craft-testkit：直接采用适用开发辅助

- native dev-dependency，生产和WASM依赖图不引入。该crate无生产第三方依赖。
- 可用rust_sources及std_instant检查实际WASM设计闭包，不扫描无关桌面原生CLI来制造误报。**不能为求绿排除commands**：当前EngineV2含std::time::Instant，应明确登记为未来Worker适配前的阻断项；当前原生P2-03通过不外推WASM通过。
- 拟在`app/kernel/crates/commands/tests/platform_boundary.rs`及`model/tests/platform_boundary.rs`记录/验证界限，正式WASM时钟改造须在相关消费者获准后进行，不在本轮偷偷改Engine。
- hostile/deadline助手只有被具名用例需要时才采用；with_deadline的线程超时不能替代现有PGID清场、RSS/盘/子进程采样和总秒监督。不能跑公共库整个workspace测试作为应用验收。
